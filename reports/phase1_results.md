# Phase 1 Benchmark Results

## Purpose

This report records the first reproducible benchmark for the transaction-fraud foundation using `fraud_ds1`.

The benchmark was executed in GitHub Actions on the project branch using a chronological 70/15/15 train/validation/test split. Model selection used validation PR-AUC, operating thresholds were selected using validation-only estimated business cost, and the final test window was not used for either decision.

## Data split

| Split | Rows | Fraud rate | Approx. fraud cases |
|---|---:|---:|---:|
| Train | 4,410 | 0.431% | 19 |
| Validation | 945 | 0.529% | 5 |
| Test | 945 | 0.741% | 7 |

The very small number of positive cases is an important limitation. A single fraud prediction can materially change precision, recall, F1, and PR-AUC. These results should therefore be treated as an initial benchmark rather than a stable estimate of production performance.

## Validation comparison

| Model | ROC-AUC | PR-AUC | Precision | Recall | F1 | Cost-selected threshold | Estimated validation cost |
|---|---:|---:|---:|---:|---:|---:|---:|
| Logistic Regression | 0.614 | 0.0126 | 0.0198 | 0.400 | 0.0377 | 0.00341 | $2,212.44 |
| Random Forest | 0.969 | 0.0884 | 0.1042 | 1.000 | 0.1887 | 0.02988 | $215.00 |
| **XGBoost** | **0.989** | **0.2227** | **0.2083** | **1.000** | **0.3448** | **0.00323** | **$95.00** |

XGBoost was selected because it had the highest validation PR-AUC. At its validation cost-sensitive threshold it caught all 5 validation fraud cases while generating 19 false-positive alerts.

## Untouched test performance

The selected XGBoost pipeline and threshold were then evaluated once on the newest 15% test window.

| Metric | Result |
|---|---:|
| ROC-AUC | **0.9647** |
| PR-AUC | **0.6732** |
| Precision | **0.3571** |
| Recall | **0.7143** |
| F1 | **0.4762** |
| Estimated decision cost | **$83.47** |

### Test confusion matrix

| | Predicted legitimate | Predicted fraud/review |
|---|---:|---:|
| Actual legitimate | 929 | 9 |
| Actual fraud | 2 | 5 |

In operational terms, the first benchmark detected **5 of 7 fraud transactions**, missed **2**, and sent **9 legitimate transactions** to the fraud-review side of the threshold.

## Interpretation

The main result is not that the project has achieved a final production-grade score. The important findings are:

1. behavioral and contextual features provide useful predictive signal beyond raw transaction amount;
2. tree boosting substantially outperformed the interpretable logistic baseline on this dataset;
3. fraud-focused PR-AUC is much more informative than raw accuracy for the highly imbalanced target;
4. threshold selection materially changes operational behavior and should remain separate from model ranking;
5. the positive sample is too small to justify aggressive hyperparameter tuning against one validation window.

## Business-cost assumption

The current threshold optimizer uses a deliberately transparent project assumption:

- missed fraud cost = transaction amount × 1.0;
- unnecessary review cost = $5 per legitimate flagged transaction.

These values are **not claimed to be real bank economics**. They exist so the project can demonstrate cost-sensitive decisioning. In a real organization they would be replaced by chargeback/recovery rates, customer-friction costs, analyst labor cost, authentication cost, and review capacity.

## Next validation improvement

Before tuning the model further, Phase 1 should add **rolling / expanding-window temporal backtesting**. This will evaluate candidate models over several historical cutoffs and aggregate fraud-focused metrics across folds instead of relying on only five fraud cases in one validation window.

The newest holdout window should remain untouched as the final test set.

## Reproducibility

The benchmark is generated by:

```bash
python scripts/benchmark_fraud_models.py
```

and automatically executed by `.github/workflows/phase1-benchmark.yml`. The workflow uploads `model_benchmark.json` and the scored test transactions as a GitHub Actions artifact.
